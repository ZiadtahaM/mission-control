ARCHITECTURE — TELEGRAM-LEVEL FAULT TOLERANCE
1. WORM / Append-Only Data (Like Telegram MTProto Storage)

    Users: NEVER hard delete. Use deleted_at soft deletes.

    Payment events: APPEND-ONLY immutable transaction log.

    Audit log: append-only event stream (userId, action, payload, timestamp).

    All critical state changes create a NEW record. Old records are never mutated.

2. Circuit Breaker Pattern (using 'opossum' library)

    Stripe API: circuit breaker with 3-failure threshold, 30s timeout

    Email service: fallback to queue with exponential backoff retry

    OAuth providers: graceful degradation (allow password login if OAuth is down)

3. Horizontal Scaling (Stateless)

    Zero in-memory state: all state in Redis or PostgreSQL

    Redis Pub/Sub for WebSocket events across multiple server instances

    BullMQ distributed queues (multiple workers process same queue)

    PostgreSQL connection pooling (max 20 connections per instance)

    Nginx upstream with least_conn load balancing

4. Dijkstra Applied to Internal Service Routing

    Service registry where each external service (email, payments, CDN) has a weight

    Weight = latency + error_rate (updated every 30 seconds)

    Route to lowest-weight endpoint using Dijkstra shortest path

    Re-weight nodes based on health metrics automatically

5. Read Replicas + Sharding

    Write to PostgreSQL primary, read from replica

    Shard users by user_id % num_shards for scale

    Dashboard queries hit read replica only
